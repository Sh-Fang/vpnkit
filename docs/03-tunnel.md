# 03 · 隧道协议

隧道复用 443 端口，与普通 HTTPS 共存。**握手不是标准 TLS 协商**：客户端发送固定的握手模板完成会话恢复。

## 1. 前提

- 服务端地址与端口来自 `conf.csp`（`svpnhost` / `svpnport`）
- 认证已完成，持有 16 字节会话令牌

## 2. 握手模板

### 2.1 ClientHello（82 字节）

```
16 03 01 00 4d 01 00 00 49 03 01 46 83 74 24 01
43 16 29 1f 95 3e c9 63 b9 fc b6 16 00 aa 20 15
eb 75 07 59 40 8b 8d 0c e1 60 43 20 b1 65 f6 7f
5a 6d 2c 54 d2 71 69 97 72 58 65 c3 40 9a 8a 0f
cd 81 d8 2e db 7b 8f f7 1b c1 80 c6 00 02 00 39
01 00
```

结构（供校验，实现时直接用上面的字节数组）：

```
16 03 01 00 4d          record: handshake, version TLS1.0, len=77
  01 00 00 49           ClientHello, len=73
    03 01               client_version
    46 83 74 24 …       random, 32 B
    20 …                session_id_len=32 + 32 B 固定会话 ID
    00 02 00 39         cipher_suites_len=2, {0x0039}
    01 00               compression_methods: null
```

自洽校验：`5 + 77 == 82` 且 `9 + 73 == 82`。

### 2.2 ChangeCipherSpec + Finished（43 字节）

```
14 03 01 00 01 01 16 03 01 00 20 2b d1 df 0e e2
4c da 7a 36 0e de 24 81 b9 79 32 67 8f f2 88 8c
ef a3 7e 50 1c 09 6b 09 9c 5a 0d
```

结构：

```
14 03 01 00 01 01       ChangeCipherSpec
16 03 01 00 20 <32 B>   Finished（固定值）
```

`6 + 5 + 32 == 43`。

### 2.3 设计含义

这两段是**预置会话凭证**：客户端不生成随机数、不做密钥交换，直接用一段既有的会话继续。
等价于把会话票据预先烧进客户端，因此**服务端必须保留对应会话状态**才能接受。

由此带来的工程约束：

- 握手字节一个都不能改（改了就是另一个会话）
- 客户端不需要 TLS 库，不需要 RC4 之外的任何密码原语
- 模板里的密码套件是 `0x0039`（DHE-RSA-AES256-SHA），但这只是模板中的一个字节：服务端在 CCS 之后**不启用** TLS 记录层加密，后续 clientMsg 以明文 `JJYY` 发出。客户端**不实现**任何 TLS 记录层。（TODO(待实测)：若联调在 76/40 步失败，日志须提示"疑似服务端期待真实 TLS"）
- 服务端会话过期会导致握手被拒，此时只能重新走认证再试

### 2.4 TODO(待实测)

> 这两个模板（以及 §4.1 的 clientMsg 5 字节前缀）是否被目标网关接受，**无法离线判定**。实现时把它们做成可替换资源
> （`internal/tunnel/templates.go`），并在失败时给出专门的错误码 `ErrHandshakeRejected`，
> 便于联调期快速定位是不是模板失效。

## 3. 连接时序

| # | 动作 | 长度 | 方向 |
|---|---|---|---|
| 1 | 建 TCP 连接 | — | → |
| 2 | 发 ClientHello | 82 | → |
| 3 | 收服务端响应 | 122 | ← |
| 4 | 发 CCS + Finished | 43 | → |
| 5 | 发 clientMsg | 76 | → |
| 6 | 收 serverMsg | 40 | ← |
| 7 | 校验 serverMsg，置就绪 | — | — |

要点：

- 第 3 步的 **122 字节读完即丢弃**，不做任何校验。实现时也必须读完再丢弃（不读会阻塞后续写）。
- 第 6 步才是真正的成败判定。
- 所有长度都是固定值，不要用「读到 EOF 为止」的方式读。

## 4. 两个消息格式

### 4.1 clientMsg（76 字节）

```
off  len  值
0    1    0x17
1    1    0x03
2    1    0x01
3    1    0x00
4    1    0x3c
5    3    00 00 00
8    4    "JJYY"          魔数
12   4    conn_type       小端 u32
16   32   00
48   16   session_token   会话令牌，默认按 ASCII 原文填入（见下）
64   8    00
72   4    尾部标志        网络序（大端）u32
```

前 5 字节 `17 03 01 00 3c` 是**原样模板**：记录头声明长度 60，但 `5 + 60 = 65 ≠ 76`，已知不自洽。
不要"修正"成 `0x47`——那等于改线格式，联不通时也分不清原因。TODO(待实测)。

尾部标志取值：

| conn_type | 偏移 72 |
|---|---|
| < 2（控制通道） | `0xFFFFFFFF` |
| 5 / 6 / 7 / 8 | `htonl(arg)`，`arg` 由调用方给 |
| 其他 | `0` |

`conn_type < 2` 是合法的控制通道建连，正常发出。（旧版本文档写"返回错误、不发出"，系对原实现中 `-1` 写入尾部的误读，已更正。）
控制通道默认发 `conn_type = 1`，可通过 `tunnel.ctrl_conn_type` 配置。TODO(待实测)。

会话令牌填入方式：默认把 TwfID 字符串的 ASCII 字节原样放入 16 字节字段；`tunnel.token_encoding = "hex"` 时改为 hex 解码后的字节。
长度与 16 不符时报 `ErrTokenLength`，**不截断、不补零**。TODO(待实测)。

### 4.2 serverMsg（40 字节）

```
off 0..3   "AABB"
off 4..7   状态码（小端 int32）
off 8..39  命令参数（见 docs/04）
```

`[0:4] != "AABB"` → 握手失败，返回 `ErrBadServerMsg`。

### 4.3 连接类型

| conn_type | 用途 | 应答状态码 |
|---|---|---|
| < 2（默认 1） | 控制通道（命令） | — 交给命令分发 |
| 5、8 | 下行（读流） | 2 |
| 6、7 | 上行（写流） | 1 |

数据通道建连时 serverMsg 偏移 4 的值是**应答码**，与控制通道上的命令码同位不同义（见 `GLOSSARY.md`）。

TODO(待实测)：选哪一个 conn_type、尾部 `arg` 填什么，原始资料未给出。实现约定：上行默认 6、下行默认 5
（`tunnel.data_conn_up` / `data_conn_down`），`arg` 填 `SEND_IP` 分配的 `tapip`（网络序 u32），
建连时打 `assumption=data_conn`。应答码不符时报 `ErrUnexpectedAck`，附 serverMsg hex。

控制通道与数据通道各自建连、各自走一遍上面的时序。

### 4.4 与 64 字节裸消息的对应关系

另有一套可用实现，把同样的信息发成 **64 字节裸消息**（不带 §4.1 那 12 字节前缀）。
两边的字段逐一对齐，差别只在长度：

| 64 字节裸消息 | §4.1 的 76 字节消息 | 含义 |
|---|---|---|
| `[0:4]` opcode，小端 | `[12:16]` conn_type，小端 | 操作/连接类型 |
| `[4:36]` **凭据前段** | `[16:48]` 原记为"保留 32 字节零" | 见 §4.4.1 |
| `[36:52]` 登录令牌 | `[48:64]` session_token | 16 字节 |
| `[52:60]` 零 | `[64:72]` 零 | — |
| `[60:64]` **倒序的分配地址** | `[72:76]` 尾部标志 | 地址，不是 `SEND_IP` 的产物 |

也就是说 `76 = 12 字节前缀 + 64 字节主体`。这解释了 §4.1 里那个"32 字节保留区"
为什么一直是零却没影响任何观察——它其实有内容，只是记录时没看出用途。

两种长度**都还没在真网关上验证过**，而且很可能只有一种被接受。
`vpnkit probe l3` 会在同一次运行里各试一次，把网关的真实回执打出来。

#### 4.4.1 凭据前段（32 字节）

这一段不来自登录响应，而是"这条 TLS 会话"的标识：

1. 建一条**真实** TLS 连接（不是 §2 的伪造握手）；
2. 用 TWFID 作 Cookie，请求 `/por/conf.csp` 和 `/por/rclist.csp`；
3. 取服务端 ServerHello 里的 session id；
4. 转成十六进制，**取前 31 个字符**，末尾补一个 `0x00`。

第 4 步是这件事唯一反直觉的地方：末位恒为 0，不是第 32 个十六进制字符。
那 32 字节在网关侧是 C 字符串缓冲区，最后一个字节留给结束符。按整数个 hex 字符填
只会差一位，但整条凭据都不对。

TLS 上限必须压到 1.2：TLS 1.3 下 ServerHello 里这个字段只是客户端随机数的回显，
服务端不分配会话，取出来没有意义。

**实测（本网关）**：TLS 1.2 会分配 32 字节 session id（`version=0x0303`、
`cipher=0xc030`），且每次连接不同。所以"哪条连接上发的请求"本身是有意义的——
隧道建连必须用同一条连接上取到的 session id。

#### 4.4.2 opcode 与回执

| opcode | 用途 | 回执首字节 | 其余 |
|---|---|---|---|
| `0` | 查询分配到的地址 | `0` | `[4:8]` 是地址 |
| `5` | 上行（写）流 | `2` | 之后是裸 IP 包流 |
| `6` | 下行（读）流 | `1` | 之后是裸 IP 包流 |

注意这是**另一套编号**，与 §4.2 的 `AABB` + int32 状态码不通用：控制通道用 4 字节状态码，
这里只用一个字节。

地址字段是**倒序**的四字节（`ip[3] ip[2] ip[1] ip[0]`）。按"网络序 u32"去填会得到
完全相反的字节序，网关要么拒绝，要么把你当成另一个地址。

## 5. 数据帧

数据通道上每个包：

```
+0   u32  opcode           小端
+4   u32  整包长度（含头）  小端
+8   u32  保留             小端，发送填 0
+12  ...  裸 IPv4 包，RC4 加密（enc != 0 时）
```

TODO(待实测)：opcode 取值与 opcode/保留字段的字节序均未验证。实现约定：

- 发送 opcode 取 `tunnel.data_opcode`，默认 `0`
- 接收不按 opcode 过滤；未见过的 opcode 在 debug 级记一次（同值只记一次）
- 长度字段解出 `< 12` 或 `> MTU + 12` 时报错，并提示"疑似字节序错误"，附 12 字节头 hex

- 12 字节头**不加密**，原样发出
- 只有 `[12:]` 经过 RC4
- RC4 状态**跨包连续**，不能每包重置（见 `docs/05` §3）

发送路径：

```go
body := pkt[12:]
rc4.XORKeyStream(body, body)   // 就地
conn.Write(pkt)                // 整包发出
```

接收路径：

```go
// 先读 12 字节头，得到 length，再读 length-12 字节体
rc4.XORKeyStream(body, body)
tun.Write(body)
```

## 6. 实现的纯函数边界

`pkg/wire` 应只包含这些无副作用函数，便于表驱动测试：

```go
func BuildClientHello() []byte                                            // 返回 82 B 副本
func BuildCCSFinished() []byte                                           // 返回 43 B 副本
func BuildClientMsg(connType uint32, token [16]byte, arg uint32) ([]byte, error) // connType<2 合法
func ParseServerMsg(b []byte) (status int32, payload []byte, err error)
func BuildDataFrame(opcode uint32, ipPacket []byte) []byte
func ParseDataFrame(b []byte) (opcode uint32, ipPacket []byte, err error)
```

全部函数返回**新分配的切片**，调用方可以自由修改。不要返回内部全局变量。
