# 06 · 设备特征码

网关用"硬件特征码"做设备绑定。原客户端每次登录都现算，本项目的目标之一是**算对一次、稳定复用**，
避免因硬件或网卡变化反复被要求重新登记。

## 1. 输出形状

一段竖线分隔的三元组，与官方 Web SDK 的旧格式逐字节一致：

```
hid|macAddress|hostName
```

| 段 | 含义 | 形状 |
|---|---|---|
| `hid` | 设备指纹本体 | 32 位大写十六进制 |
| `macAddress` | 参与计算的网卡 MAC | `aa-bb-cc-dd-ee-ff`（小写、连字符） |
| `hostName` | 主机名 | 标准 base64（带 `=` 补位） |

`hid` 是网关真正比对的那一段；后两段是随行的本机信息。
`auth/hid` 这步的提交字段映射见 `docs/02` §4.2。

## 2. 取值优先级

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | 本地固化文件 | 存在即直接用，不再计算（保证稳定） |
| 2 | 实时计算 | 磁盘序列号 + 物理网卡 MAC + 主机名 |

实时计算在 Linux 上需要读块设备，因此**需要 root 或 `CAP_SYS_RAWIO`**；
普通用户跑出来的是"只有 MAC 参与"的降级值，与官方客户端的结果不同，`devid show` 会明确提示。

## 3. 算法

### 3.1 第一步：磁盘序列号

按 `/dev/sda`、`sdb`、`sdc`、`sdd`、`hda`…`hdd` 的顺序找第一块能读出 ATA 序列号的盘。
每块盘走两步：

1. `ioctl(fd, HDIO_GET_IDENTITY)` 探测这是不是 ATA 设备；失败就换下一块
2. `ioctl(fd, SG_IO)` 发 **ATA PASS-THROUGH(16)** 封装的 **IDENTIFY DEVICE**

```
CDB = 85 08 2E 00 00 00 00 00 00 00 00 00 00 40 EC 00
      │  │  └─ T_TYPE/方向/长度        │  └─ DEVICE (LBA)
      │  └─ protocol = PIO data-in     └─ 0x40
      └─ ATA PASS-THROUGH(16)                命令 0xEC = IDENTIFY DEVICE
```

`sense` 缓冲区只用来确认传输成功（`status ∈ {0,2}`、`host_status = 0`、`driver_status = 8`），
不对它做其他解读。

序列号取自应答的**第 10–19 字（字节 20 起，共 20 字节）**，还原规则：

1. 逐字按"高字节、低字节"的顺序展开（ATA 字符串在大端意义上存储，原始字节是配对交换的）
2. 丢掉值为 0 的字节
3. 跳过开头"两个字都是空格"的前导字；若停在一个高字节为空格的字上，把它的低字节单独吐出，再从下一个字继续
4. 末尾补一个 `\n`

第 4 步是原客户端的行为：**那个换行会参与后面的 MD5**，不能省。
现实的 ATA 序列号字段是**前导空格右对齐**的，所以第 3 步是必需的。

### 3.2 第二步：折叠成分指纹

```
acc = md5hex(serial + "\n")          // 磁盘这路
acc = fold(acc, md5hex(macAddress))  // 网卡这路，磁盘取不到时 acc 就是它
hid = acc
```

`md5hex` = 16 字节 MD5 的大写十六进制展开（`0123456789ABCDEF` 字母表）。

`fold` 是逐字符折叠，**取的是字符码点低四位的和对 16 取余**：

```
fold(a, b)[i] = "0123456789ABCDEF"[(a[i] % 16 + b[i] % 16) % 16]
```

注意这不是"十六进制位值相加"：`A` = 0x41，`0x41 % 16 = 1`，所以 `A` 在这里的"值"是 1 而不是 10。
这是原客户端的实际行为，**不要"修正"成直觉版本**，否则网关认不出来。

### 3.3 第三、四步：MAC 与主机名

**MAC**：用 `ioctl(SIOCGIFHWADDR)` 取，格式化成 `%02x-%02x-%02x-%02x-%02x-%02x`（小写、连字符）。

选哪张网卡，按原客户端的判据：

1. 枚举 `/proc/net/dev` 里的接口
2. **物理网卡**的判据是 `/sys/class/net/<if>/device` 存在（有真实硬件），不要用名字前缀猜
3. 物理网卡放进集合，按**接口名排序**后取第一个 MAC 非全零的
4. 一张物理网卡都没有时，退到非物理网卡按同样规则取

排序很关键：同时插着网线和连着 Wi-Fi 时，`enp3s0` 排在 `wlp2s0` 前面，**参与计算的是有线网卡**。

**主机名**：`uname()` 的 `nodename`，做标准 base64。主机名为空则是空串。

### 3.4 拼起来

```
hid|macAddress|hostName
```

磁盘和网卡都取不到时返回明确错误，不返回空串。

## 4. 已验证的黄金向量

实测机：磁盘 `WD-WXP1E278DWSN`、网卡 `54-ee-75-e0-3f-c5`、主机名 `oasis-Lenovo`。

| 中间量 | 值 |
|---|---|
| `md5hex(serial + "\n")` | `DD0A972BDC1723886A98315F622A30E0` |
| `md5hex(mac)` | `D98AB73B269C30DB2F4C83B7C561C906` |
| `fold(...)` → `hid` | `8D82BE5469AA53CA87DBB47D97826956` |
| `base64(hostname)` | `b2FzaXMtTGVub3Zv` |
| 整串 | `8D82BE5469AA53CA87DBB47D97826956|54-ee-75-e0-3f-c5|b2FzaXMtTGVub3Zv` |

`internal/devid` 的单测直接锁死这组值。

这组值不是"推算出来就算数"，而是拿原客户端自己的实现逐字节核对过的：

- 在同一台机器上（宿主网络/UTS 命名空间、root 权限），直接调用原客户端里合成特征码的那个函数，
  它返回的整串就是上表最后一行，与本项目的 Go 实现**逐字节相同**；
- 把"是否纳入网卡 MAC"这个开关关掉，它返回的第一段是 `DD0A972BDC1723886A98315F622A30E0`，
  正好等于 `md5hex(序列号 + "\n")`，说明磁盘这路的解码（含前导空格剥离与补换行）也对上了；
- 换成容器自己的网络命名空间时，第二段变成容器网卡的 MAC、第三段变成容器主机名的 base64，
  说明"哪张网卡""主机名怎么编码"同样一致。

也就是说 `docs/06` 这一节的算法不是猜测，是与原实现比对过的。

## 5. 缓存与固化

路径 `~/.config/vpnkit/device-id`，内容是整串三段值，权限 `0600`。

规则：

- 读到即用，不校验来源
- 内容非法（第一段不是 32 位大写十六进制）时视为不存在，重新计算
- 文件里只有第一段时（早期版本写下的），另两段用本机现值补齐
- `devid pin <值>` 写入指定值；`devid pin` 不带值时固化本机当前算出的值；`devid show` 打印三段值、来源与取数细节

### 5.1 为什么要固化

原客户端每次实时计算，本机插拔扩展坞、换 Wi-Fi、起 docker 都会改变参与计算的网卡集合，
于是同一台机器算出不同的值，网关判为"陌生设备"要求重新审批——这正是"每次都要机器码"的成因。

> **本机首次成功登记后就用 `devid pin` 固化，之后本机始终发送同一个值。**

代价是它与"当时的硬件"解绑：换机器必须删掉 `device-id` 重新固化，否则两台机器共用一个指纹。

使用边界：

- 只用于固化**本机自己**的指纹；不得把一台机器的值拿到其他机器上用，那属于绕过网关管理方的绑定策略
- 使用本工具前应取得网关管理方对第三方客户端的认可

## 6. 自动固化

用 `--register-device` 登录成功后，客户端会把本次用的三段值自动写进 `device-id`
（即 `devid pin` 的效果）。`devid pin` 仍然是显式覆盖入口。

## 7. 隐私说明

特征码可反推硬件信息（磁盘序列号、MAC 前缀含厂商）。因此：

- 只在登录流程中发送；是否发送由 `auth.send_device_id` 决定（`docs/09` §3）
- 绑定申请（`docs/02` §4.3）**默认关闭**：它会把本机登记进网关的设备绑定队列，是有副作用的写操作
- 三段值属于身份凭据，按 `AGENTS.md` 的红线要求：不进仓库、日志里掩码（保留首尾各 4 字符）；
  只有用户显式执行 `devid show` / `devid pin` 时才完整打印
- `status --json` 默认不包含该字段，需显式 `--show-devid`

## 8. 平台差异

| 平台 | 状态 |
|---|---|
| Linux | 已实现，并与原实现逐字节对拍（§4） |
| Windows | 取数未实现，`diskSerial` 返回 `ErrUnsupported`，只剩 MAC 这路 |
| macOS | 取数未实现 |

### 8.1 与 Windows 实现的比对结果

已核对的底层原语在两边**完全一致**：

| 原语 | Windows | Linux |
|---|---|---|
| 摘要 | MD5（`MD5Init/Update/Final` 三件套，上下文 88 字节） | MD5 |
| 十六进制表 | `"0123456789ABCDEF"`（大写） | 同 |
| MAC 取法 | `GetAdaptersInfo`，取 `Type == 6` 或以 `0x47` 结尾，跳过 Loopback | `SIOCGIFHWADDR`，由 sysfs 判定物理网卡 |
| MAC 文本 | `%02x-%02x-%02x-%02x-%02x-%02x` | 同 |
| 主机名 | 走 Base64 | 同 |
| 输出 | 32 位大写十六进制 | 同 |

**但要素的合成方式不一样**，这一点必须注意：

- Windows 是**三选一**：缓存文件 > 网卡 MAC > 卷序列号，选中的那一个直接做 MD5；
- Linux 是**两路折叠**：磁盘序列号与网卡 MAC 各自做 MD5，再逐字符折叠（§3.2）。

所以两平台算出的 `hid` 不是同一套推导，**固化值不能跨平台搬运**。
`device-id` 只在本机本平台有效（§5 的使用边界），换平台必须重新算、重新登记。

macOS 实现尚未核对，不要假定它与上面任一个相同。

macOS 与 Windows 客户端的算法尚未逐字节核对，不要假定与 Linux 完全一致。

## 9. 测试

| 用例 | 期望 |
|---|---|
| 黄金向量（§4） | 三段的每一个中间量都对上 |
| 有固化文件 | 直接返回，不枚举网卡 |
| 固化文件只有第一段 | 另两段用本机现值补齐 |
| 磁盘取不到 | 第一段退化为 `md5hex(mac)`，不报错 |
| 磁盘与网卡都取不到 | 返回 `ErrNoFingerprintSource`，不返回空串 |
| 有磁盘无网卡 | 第二段补 `00-00-00-00-00-00`，第一段仍只有磁盘参与 |
| 序列号前导空格 | `decodeSerial` 剥掉空格，得到裸序列号 |
| 第一段形状 | 恒为 `[0-9A-F]{32}` |
